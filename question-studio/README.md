# AkadilEDU Question Studio

A local browser workspace for generating and reviewing original UNT mathematics practice questions through the OpenAI API. It uses the project's existing Firebase Realtime Database and Cloud Storage.

## Run

Install dependencies with `npm ci` inside `question-studio`. Copy `.env.example` to `.env` and supply all required values. `STUDIO_ENV_FILE` can reference the existing project's environment file for Firebase credentials and the API key. Studio settings take precedence over that file.

Use Node.js 22.18 or newer. Run `npm run check`, then `npm start`. Open the exact `STUDIO_PUBLIC_ORIGIN` configured in `.env`. The host must be a loopback address and the origin must match the configured host and port. Keep the process and computer running while generation is active.

`OPENAI_MODEL`, API endpoint, token prices, reasoning effort and maximum output tokens are explicit settings. Verify model access and current prices before starting. `STUDIO_BUDGET_USD` cannot exceed the authorized $50. This is the studio run's API budget, not an account-wide spending limit and not a Firebase billing limit.

`OPENAI_MODEL` handles question creation, translations and geometry research. `OPENAI_REVIEW_MODEL` handles the separate solution and quality review, with its own four `OPENAI_REVIEW_*_PRICE_PER_MILLION` settings. Reservations and actual charges use the selected role's prices. Both roles share the same total budget. Previously completed requests retain their original models, prices and results when either role changes.

`OPENAI_SERVICE_TIER` selects `default`, `fast` or `ultrafast`; configure matching token prices for both model roles. Ultrafast uses synchronous creation with its service header; other tiers use background creation. Each request records its model, tier and prices, so switching models preserves historical costs. Switch only after outstanding unquarantined calls have settled. Historical quarantined reservations remain recorded under their original funding scope. For runs created before price snapshots existed, supply `OPENAI_LEGACY_MODEL` and the four `OPENAI_LEGACY_*_PRICE_PER_MILLION` values matching the original run. Existing completed questions keep their actual authoring model; reviewer identity is recorded separately.

## Workflow

The topic list comes from live `/topics`. Only exact boolean `isLast === true` nodes are eligible; the service node `RANDOM` is excluded. Geometry and mathematical literacy are included. Cycles and missing parents stop loading instead of creating a misleading topic path.

The initial per-topic quantity is an estimate within `STUDIO_TOPIC_MIN_QUESTIONS` and `STUDIO_TOPIC_MAX_QUESTIONS`. The authoring model recommends a distinct compact target and coverage goals: narrow subtopics near the minimum, ordinary subtopics around 8–12 questions, and broader subtopics near the maximum only for real missing skills. Existing accepted questions are preserved. Difficulty selection within each topic aims approximately at the custom training-bank mix of 25% easy, 45% medium and 30% hard; this is not the official exam distribution.

The local generator completes one leaf topic before selecting the next in topic-path order. A separate API coverage audit maps the topic to the 2026 [profile mathematics curriculum](https://new.testcenter.kz/wp-content/uploads/2025/10/09_%D0%9C%D0%B0%D1%82%D0%B5%D0%BC%D0%B0%D1%82%D0%B8%D0%BA%D0%B0_%D0%BA%D0%B0%D0%B7.pdf) or [mathematical literacy curriculum](https://new.testcenter.kz/wp-content/uploads/2025/10/07_%D0%9C%D0%B0%D1%82%D0%B5%D0%BC%D0%B0%D1%82%D0%B8%D0%BA%D0%B0%D0%BB%D1%8B%D2%9B-%D1%81%D0%B0%D1%83%D0%B0%D1%82%D1%82%D1%8B%D0%BB%D1%8B%D2%9B.pdf), distinguishes explicitly listed material from prerequisites, checks actual question IDs against coverage goals, and records missing skills. Topics with enough questions are audited before being marked complete. Only adequately covered topics are marked complete. Unresolved or out-of-scope topics remain visibly deferred. This original single-answer practice bank does not implement every official exam question format, and model review is not certification.

`STUDIO_CONCURRENCY` is a ceiling of 1–50 simultaneous local tasks, not a promise of that many active requests. Multiple generation batches and up to `STUDIO_REPAIR_CONCURRENCY` corrections can work within the current topic. A batch size of one permits shorter independent requests; assignments identify distinct coverage goals. Outstanding generation and repair slots count against the remaining topic target, so increasing concurrency does not increase the planned bank size. The first planning batch finishes before parallel assignments are created for an unplanned topic. On resume, topics with saved batches are selected first, with their response IDs intact. All tasks and coverage audits share serialized budget admission and persisted reservations. Image rendering remains serialized, while uploading and saving the previous image can overlap with rendering the next question. A transient local screenshot timeout retries rendering the saved question instead of paying to generate it again. The Apps Script worker retains its separate scheduling implementation.

`STUDIO_COVERAGE_REASONING_EFFORT` and `STUDIO_COVERAGE_MAX_OUTPUT_TOKENS` configure the separate topic-coverage audit; mathematical question reviews retain their own review settings. Coverage rework is bounded by `STUDIO_MAX_TOPIC_FAILURES`. A topic that cannot satisfy its goals within this allowance remains deferred rather than spending indefinitely on the same findings.

Kazakh questions use native school terms such as ЕҮОБ and ЕКОЕ; Russian questions use НОД and НОК. The same terminology rules apply to statements, options, explanations, hints and drawings. Remainders are explained through elementary division, divisibility and repeating patterns rather than unexplained `mod` notation. Deterministic guards queue existing matching records for API correction and independent review.

Each question has equivalent Kazakh, Russian and English statements, choices, explanations and hints, a shared zero-based correct answer, and provenance. A separate API request solves and reviews the generated batch. Failed mathematical, translation, topic, difficulty, diagram or format checks keep a question unpublished. Rejected questions enter an automatic repair queue: the authoring model receives the reviewer’s concrete findings, proposes a complete correction, and the separate review model checks the revised question again. Accepted corrections replace the rejected version under the same question ID. The original and subsequent findings, response IDs and repair attempt count remain in the audit history. The panel shows queued, running, completed and exhausted repairs; exhaustion leaves a question unpublished and does not prevent other questions from being processed. AI review reduces errors but does not certify correctness.

Question statements use ordinary Unicode math when practical. Necessary LaTeX is limited to the statement and rendered locally. Options, explanations, hints and labels must be plain Unicode. Visual questions include structured diagram geometry. Diagram PNGs omit the statement; identical drawings share one uploaded image across languages. Translated labels produce separate images only when their visible content differs. A localized prose prefix followed by standalone LaTeX blocks is split into text and a formula image. Identical formula/drawing content reuses one PNG and one Storage object across languages. The original statement stays in local state for review and re-rendering; Firebase receives the separate display text with `imageContainsStatement=false`. Interleaved prose and formulas retain their original order in a full statement image with `imageContainsStatement=true`. Diagram-only images also carry `false` so the bot displays the localized statement. Missing flags retain legacy behavior. Captions are accessibility metadata, while essential information belongs in the statement or visible labels. Exported PNGs are cropped to the visible ink, preserving thin formula and diagram strokes, then receive a 24-pixel white border on every side. Short formulas no longer inherit the full browser canvas width. The renderer does not execute model-supplied SVG or HTML.

The diagram conventions were checked against the NTC's [Russian sample, page 3](https://testcenter.kz/wp-content/uploads/2024/12/obr_var_test_16.pdf) and [English sample, pages 2 and 4](https://testcenter.kz/wp-content/uploads/2025/06/MATHEMATICS.pdf): readable vertex labels, angle arcs, right-angle marks, dashed hidden edges and selective region shading. Ellipse arcs support projected circular rims. Measured label placement avoids overlaps and clipping; diagrams that cannot be arranged legibly are rejected. These original practice questions are not official NTC exam items.

Statement fractions, compound logarithm bases, long indices, nested radicals and dense formulas must pass a deterministic readability check before publication. These expressions are repaired through the API into delimited LaTeX and rendered as statement images. Options remain single-line Unicode text, at most 64 UTF-16 characters per option in every language; authors should aim for 40 or fewer. Long classifications must be reformulated rather than truncated or moved into answer images. Startup audits existing validated questions against this policy. Matching generated records are temporarily changed to drafts and queued for correction under their existing IDs; externally changed records are left untouched. Each correction undergoes independent review, including comparison with the original task.

## Geometry references

With `STUDIO_WEB_SEARCH_ENABLED=true`, the worker researches each geometry leaf topic once through the API's real web search tool and caches the result. `STUDIO_WEB_SEARCH_MAX_CALLS` limits built-in calls per research response. Research reserves `STUDIO_WEB_SEARCH_INPUT_TOKEN_RESERVE` input tokens plus maximum output and tool fees before dispatch, within the same total budget. Search fees use `OPENAI_WEB_SEARCH_PRICE_PER_CALL`.

Only source URLs returned by the search tool are retained. The question preview links to reference sources, and Firebase provenance records the research response. Sources inform methods, coverage and diagram conventions for original questions; the pipeline does not bulk-copy collections. No-search or empty results are reported honestly and cached. Research failures retain their call ID for recovery instead of issuing an automatic paid replacement.

Validated questions are stored under `/questions`, with `/questionsByTopic` membership. `STUDIO_AUTO_PUBLISH=true` publishes accepted questions; `false` saves drafts for manual publication in the studio. Manual publication requires validated questions and a stopped worker. Bot practice, channel campaigns, review and the admin editor understand the same translations.

## Source parsing

Choose source parsing and paste text that you are entitled to process. The model extracts complete questions, independently solves them and classifies them into eligible leaf topics. Every processed source prefix must match the original exactly. Incomplete or ambiguous material stops with a visible error and retained input; it is not silently discarded or invented.

Saved batches take priority when generation resumes. The global audit of already populated topics runs after saved jobs and known topic deficits have been handled, with up to `STUDIO_COVERAGE_CONCURRENCY` audits in parallel. Per-topic coverage checks still apply before completion. Each audit uses the same persisted reservations. Pending audit IDs survive pauses.

The local dashboard polls compact question summaries and loads the selected question separately, keeping a small detail cache. Cloud mode retains its existing response format. Concurrent local saves are coalesced within an event-loop turn; API calls still wait for their reservation to be persisted before submission.

## Costs and recovery

Local state uses `state.sqlite` with WAL transactions and full synchronous durability. Each save writes changed records rather than replacing the complete question and API history. Budget reservations commit before API dispatch. `STUDIO_STATE_WRITE_TIMEOUT_MS` bounds database lock waits; storage failures stop dispatch. An existing `state.json` is imported automatically only when the database is empty and remains as the pre-migration backup. Once imported, the SQLite database is authoritative. Keep it and any adjacent WAL/SHM files together when backing up a running process; stopping the process first is preferable. Cloud bootstrap reads the same authoritative database. Browser polling uses revision tags and skips unchanged responses, while forecast indexing avoids repeatedly scanning the full question history for every API call.

`STUDIO_RECOVERY_BACKOFF_MS` controls the recovery delay after prolonged temporary response-retrieval failures. The worker honors a longer provider `Retry-After`, preserves the existing response ID and reservation, and resumes retrieving the same request when connectivity returns. Pausing interrupts this recovery wait. Authentication failures and inconsistent accounting remain explicit stops.

At process startup, local request admission waits for one successful creation before allowing parallel creation. Response IDs commit before full response validation, so an unexpected response shape does not discard a recoverable ID. Submission failures retain their HTTP status, provider request ID and redacted error message. Explicit request validation or authentication rejections settle at zero cost and stop admission. An HTTP 429 rejection settles at zero cost and delays admission across local jobs. Retries honor the recovery backoff, a longer provider `Retry-After` and the configured attempt limit. An insufficient-quota response stops new requests. Transport failures or server errors without a response ID retain their full reservation. Admission waits for active submissions to finish and a recovery backoff, then requires one successful probe before expanding parallel creation again. Every probe needs its own reservation. `STUDIO_API_TIMEOUT_MS` bounds each local HTTP request.

`STUDIO_API_MAX_ATTEMPTS` bounds automatic replacement requests after known recoverable API failures. A response that ends at `max_output_tokens` may be retried with a larger output allowance, capped by `STUDIO_RETRY_MAX_OUTPUT_TOKENS`. Each attempt retains its own response ID, usage, price snapshot and retry links. Both the failed attempt and its replacement count toward the same budget. Terminal responses without usage are quarantined with their entire reservation retained; the affected work can continue with a separately reserved request. Authentication failures, inconsistent price data and monetary reservation overruns remain explicit stops.

`STUDIO_REPAIR_MAX_ATTEMPTS` bounds correction rounds for each rejected question. `STUDIO_MAX_TOPIC_FAILURES` bounds consecutive request failures for a topic in generation mode; exhausted topics are deferred while other eligible topics continue. Pausing preserves the current attempt, and resuming continues from saved request IDs. Reaching the total budget prevents further paid calls, including retries and corrections.

Before each paid request the studio persists a conservative reservation for input and maximum output tokens. Output accounting includes reasoning tokens. A request cannot start if it could exceed the remaining budget. Completed requests use the API's reported token usage and configured prices; uncertain requests retain their reservation.

Ordinary input, cache reads and cache writes are charged separately. `OPENAI_CACHE_WRITE_PRICE_PER_MILLION` is the full write price for the model's default cache duration. The studio does not request extended cache retention; unexpected 12-hour writes or inconsistent usage stop processing with the reservation retained. Historical corrections require retrieving actual response usage and using the original request's price snapshot.

The price forecast uses completed batches produced by the current model pair, including their rejected work, repair rounds, research, independent reviews and linked API retries. Each related call is charged once in the sample. Batches still being repaired are excluded until their outcome is known. Missing accounting links hide the forecast instead of presenting an underestimated price; actual recorded spend and reserves remain visible. The forecast changes as more tasks are processed. It is an estimate, not a promise of quantity. A quality-first model may exhaust $50 before reaching every topic's desired coverage.

An explicitly authorized new API credential may open a separate funding checkpoint, capped at $50. Its fingerprint prevents an accidental repeat reset. All earlier calls, their original prices, unresolved reservations and the preceding funding summary remain in the history. The panel separates new spending from prior spending; key rotation alone never authorizes another budget.

A user-confirmed reconciliation against OpenAI Usage can close quarantined requests under a dashboard checkpoint. It records the reported spending, timestamp and exact call IDs. This requires explicit evidence from the user; the worker never infers a zero charge from a timeout or server error. Independently confirmed token charges remain included in the active budget.

State, API response IDs, review results and local images are kept in `STUDIO_DATA_DIR`. Pausing preserves the current request and its result. Resuming retrieves the same background response rather than repeating the paid request. An uncertain request with a known response ID is retrieved before new local work starts. If a submission loses its response ID, its maximum reservation remains quarantined; a separate replacement can proceed only within the same remaining budget. Never manually clear uncertain charges or reset the ledger to make room for more requests.

Use one studio process per data directory. A process lock prevents concurrent writers. Do not delete the data directory to reset the displayed spend: that would discard the run's accounting. Credentials, local configuration and the default `.data` directory are excluded from Git.

Firebase billing is separate. Text is stored in Realtime Database; only needed images are stored in Cloud Storage. Download volume and other existing project services also affect charges. A Google Cloud budget alert alone does not impose a spending cap.

Web-search reservation checks count paid `search` actions, separately from the total `web_search_call` items (which can also contain page opens and in-page finds). Saved usage still includes all input/output tokens. Every settled call is checked against its monetary reservation before further API work. If extra paid searches fit that reservation, the response is retained, further web research is disabled and generation continues with cached references. A monetary overrun stops new requests. An uncertain charge keeps its full reservation; known response IDs are retrieved without another paid creation request.
